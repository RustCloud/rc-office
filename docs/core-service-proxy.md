# Задача для ядра: прокси сервиса плагина (Collabora через порт облака)

Кто просит: плагин [rc-office](https://github.com/RustCloud/rc-office) («Офис», Collabora Online по WOPI).
Ядро: `/home/user/projects/rustcloud`, API плагинов сейчас 0.2.14 (коммит `e9588eb`).

## Зачем

Сейчас Collabora должна быть доступна по двум путям, и администратор следит за тремя адресами:

| Кто куда ходит                    | Как сейчас                                     | Чем плохо                         |
|-----------------------------------|------------------------------------------------|-----------------------------------|
| браузер → Collabora (редактор, WebSocket) | напрямую, `office_url` = `http://host:9980` | Collabora открыта наружу: свой порт, TLS, ЦС, `frame_ancestors` |
| плагин → Collabora (discovery)    | `http.fetch` на `office_url`                   | тот же адрес должен работать и с сервера |
| Collabora → облако (WOPI)         | `wopi_base_url` или адрес панели               | должен совпадать с `aliasgroup1` в compose |

На стенде из-за этого «Unauthorized WOPI host» — `aliasgroup1` и `wopi_base_url` разошлись.

**Цель:** администратор пишет **один** адрес — внутренний адрес Collabora (`http://collabora:9980`),
браузер ходит только на адрес облака (`:8080` / `https://cloud.example.com`), в compose у Collabora нет
ни `aliasgroup1`, ни `ports`. Так же, как в Nextcloud (`richdocuments` + `proxy.php`).

```text
Браузер ──(только адрес облака)──▶ RustCloud ──прокси, вкл. WebSocket──▶ collabora:9980
                                       ▲                                     │
                                       └──── WOPI: http://<облако изнутри>:8080 ◀┘
```

Почему это ядро, а не плагин: маршруты плагина не умеют WebSocket (а редактор Collabora держит его всё
время), каждый ответ плагина идёт с CSP `sandbox` (интерфейс Collabora без своего origin не работает),
и всё, что проходит через плагин, ограничено 16 МБ и 60 с на вызов (`docs/dev/plugins.md`, «Лимиты»).

Что уже проверено на Collabora (CODE 26.04.5.2, стенд `rustcloud-test`): в её `coolwsd.xml` по умолчанию
`<alias_groups mode="first">` без групп — «первый WOPI-хост после запуска становится единственным
доверенным». То есть без `aliasgroup1` она сама доверится облаку, если облако первым к ней пришло.

## Что сделать в ядре

### 1. Манифест: `[[proxy]]` (crates/plugin-api/src/manifest.rs)

```toml
[permissions]
network = ["{office_url}"]       # как сейчас: discovery с сервера

[[proxy]]
target = "{office_url}"          # куда пересылать: адрес или {настройка}, как в network
paths = ["/browser", "/cool", "/hosting"]   # пути облака, которые уходят в target
```

- `target` — разбирается как запись `network` (`resolve`/`NetworkRule::from_url`): адрес или `{key}`
  текстовой настройки. Пустая настройка — прокси нет (как с `frame` сейчас).
- `paths` — префиксы путей **в корне облака**. Корень, а не `/app/<id>/…`: Collabora сама ссылается на
  `/browser/<hash>/…`, `/cool/<WOPISrc>/ws`, `/hosting/…` абсолютными путями. Префикс под `/app/<id>/`
  потребовал бы от Collabora `net.service_root` — снова её настройка в compose (можно оставить как
  второй вариант, см. «Открытые вопросы»).
- Проверки при разборе: каждый префикс начинается с `/`, без `..`, `//`, `?`, `#`, без `/` в конце,
  1–8 префиксов; запрещены пересечения с путями ядра (`/api`, `/app`, `/assets`, `/health`,
  `/.well-known`, `/app-sdk.js` и маршруты SPA панели — список держать рядом с роутером) и с префиксами
  других **запущенных** плагинов (при включении второго такого плагина — ошибка с понятным текстом).
- Это право: входит в `Permissions::is_none`, показывается администратору при включении («Пересылать
  `/browser`, `/cool`, `/hosting` на http://collabora:9980»), обновление, которое добавляет или меняет
  `[[proxy]]`, отключает плагин до подтверждения — как новые адреса `network`.
- Версия API — 0.2.15 (поле в манифесте и импорт из п. 3).

### 2. Сам прокси (новый модуль, например crates/server/src/service_proxy.rs)

Маршрут в `app()` (crates/server/src/lib.rs) **до** `fallback(web::serve)`, вне `CompressionLayer`
(тела идут потоком, сжатие ломает `Content-Length`/диапазоны). Для запроса ищем самый длинный
совпавший префикс среди запущенных и утверждённых плагинов (как `Plugins::frame_origins` берёт
настройки через `plugin.values`), target — из их настроек на момент запроса (настройка поменялась —
прокси пошёл по новому адресу без перезапуска).

**HTTP:**
- Пересылать метод, путь и query как есть, тело запроса и ответа — потоком (`reqwest` уже в
  зависимостях: `Body::wrap_stream` / `bytes_stream`), без буферизации и без лимита данных плагинов
  (у Collabora загрузки/выгрузки документов и бандлы JS по несколько МБ).
- Заголовки запроса: убрать hop-by-hop (`connection`, `keep-alive`, `te`, `trailer`,
  `transfer-encoding`, `upgrade` — кроме WebSocket, `proxy-*`); `Host` — **исходный** (адрес облака:
  из него Collabora строит адреса страницы); добавить `X-Forwarded-For`, `X-Forwarded-Proto`,
  `X-Forwarded-Host` (с учётом `trusted_proxies`, т. е. из `client_info`, а не сырые).
- **Не отдавать сервису учётные данные облака:** вырезать cookie сессии (`SESSION_COOKIE` из
  rustcloud-auth) из `Cookie`, вырезать `Authorization`. Остальные cookie — пропускать (у сервиса могут
  быть свои).
- Заголовки ответа: убрать hop-by-hop; вырезать `Set-Cookie` с именем cookie сессии облака; редиректы
  не проходить — отдавать браузеру, `Location` с origin target переписывать на исходный origin.
- CSP: **не** ставить `sandbox` плагинов и CSP панели — оставить заголовки сервиса как есть
  (Collabora ставит свой `Content-Security-Policy` с `frame-ancestors`; «coolwsd и WOPI-хост
  разрешены всегда», хост coolwsd она берёт из `Host` — проверить на стенде, что панель может её
  встроить).
- Таймауты: на соединение — да (несколько секунд, `502 SERVICE_UNREACHABLE`); на ответ — длинный
  (сохранение большого документа), не 60 с плагинов.

**WebSocket** (`Upgrade: websocket`, редактор: `/cool/<WOPISrc>/ws?…`):
- Проще и надёжнее всего — туннель: принять апгрейд со стороны браузера (`hyper::upgrade::on`),
  открыть к target HTTP/1.1-запрос с теми же `Upgrade`/`Sec-WebSocket-*` заголовками, дождаться
  `101`, отдать браузеру `101` с заголовками сервиса и дальше `tokio::io::copy_bidirectional` между
  двумя апгрейженными соединениями. Кадры не разбирать (не нужен `tokio-tungstenite`, не теряются
  расширения/сжатие).
- Без таймаута простоя (Collabora держит соединение, пока открыт документ; пинги она шлёт сама),
  закрыть обе стороны, когда закрылась одна. Предел числа одновременных туннелей на сервер — разумная
  страховка (настройка `[plugins]` или константа).

**Доступ:** по умолчанию — только вошедшему пользователю (cookie сессии облака; страница Collabora,
её скрипты и WebSocket открываются с того же origin, что панель, `SameSite=Lax` cookie уходит).
Иначе внутренняя Collabora окажется открыта всему интернету через облако. Без сессии — `401`.
Проверка CSRF (`X-Requested-With`) к прокси не применяется: Collabora шлёт формы (POST с
`access_token`) и XHR без этого заголовка, а сам прокси не меняет данные облака. Если позже
понадобятся анонимные редакторы (публичные ссылки) — поле `auth = "none"` в `[[proxy]]`, отдельным
решением.

**Журнал/лог:** `debug` — метод, префикс, статус, время; target недоступен — `warn` (как ошибки
`http.fetch`). Query в лог не писать: у Collabora в нём `access_token` и `WOPISrc`.

### 3. Адрес облака «изнутри» для плагина (WOPISrc)

Collabora ходит к облаку сама, по адресу из `WOPISrc`. Плагин не знает, как Collabora видит облако
(`rustcloud:8080`? `172.19.0.3:8080`? `127.0.0.1:8080`?), — сейчас это настройка `wopi_base_url`.
Ядро может узнать это само:

- При первом обращении к target (и при смене настройки / после ошибки) ядро открывает TCP-соединение
  к хосту:порту target и берёт **локальный адрес** этого соединения (`TcpStream::local_addr`) — это
  адрес облака в той сети, где живёт Collabora (в compose — IP контейнера rustcloud, на одном хосте —
  `127.0.0.1`). Плюс порт, на котором слушает сервер (из конфига `bind`), схема `http`.
- Отдать плагину новым импортом, например:

  ```wit
  interface proxy {
      /// How the service of this app's [[proxy]] reaches this server:
      /// `http://172.19.0.3:8080`; none without a proxy or when it can't be told.
      self-url: func() -> option<string>;
  }
  ```

  (или полем рядом с `settings.values` — как удобнее ядру).
- **Host-guard** (`network::guard`, `accepts_host` при `only_listed_urls`): запрос Collabora придёт с
  `Host: 172.19.0.3:8080`, которого нет в списке адресов сервера, — `400 HOST_NOT_ALLOWED`. Нужно
  принимать «адрес изнутри» (тот же `self-url`) как разрешённый Host — лучше только для запросов
  с IP-адреса target и только на `/app/<id>/…` этого плагина.

Ограничение: IP контейнера может смениться при пересоздании, а Collabora в режиме `first` помнит
первого хоста до своего перезапуска. Смягчения (по желанию): брать имя вместо IP — обратный DNS
(PTR) встроенного DNS Docker отдаёт имя контейнера, оно переживает пересоздание; а `wopi_base_url`
в плагине остаётся как ручное переопределение для нестандартных схем.

### 4. Панель (web/)

- `openFrame` (web/src/components/AppFrame.svelte, `openService`) сейчас пускает только origin из
  `apps.frames[id]`. Нужно разрешить и **свой origin**, если путь URL начинается с префикса
  `[[proxy]]` этого плагина (список префиксов отдавать в `/api/v1/apps` рядом с `frames`).
- CSP панели (crates/server/src/web.rs, `page_csp`) уже содержит `frame-src 'self'` и
  `form-action 'self'` — для прокси ничего добавлять не надо; адрес Collabora из CSP уходит сам,
  когда rc-office уберёт `frame = ["{office_url}"]`.
- **Важно для безопасности:** iframe сервиса — `sandbox="allow-scripts allow-same-origin …"`. С
  содержимым того же origin это фактически без песочницы: JS Collabora может трогать DOM панели и
  делать запросы к API от имени пользователя (как и в Nextcloud). Это и есть цена «одного адреса»:
  Collabora, которую поставил администратор, становится доверенной. Отразить в окне утверждения
  `[[proxy]]` и в docs.
- Сообщения сервиса: сейчас фильтр `event.origin === service.origin` — у прокси он совпадёт с origin
  самой панели. Добавить проверку `event.source === serviceFrame.contentWindow`, чтобы чужие окна того
  же origin не выдавали себя за сервис; `postToFrame` — на `serviceFrame.contentWindow` с этим origin.

### 6. Тесты (crates/server/tests/api.rs и юнит-тесты манифеста)

- Разбор `[[proxy]]`: корректные/некорректные префиксы, пересечение с `/api`, `/app`, с другим
  плагином; право в `is_none`; обновление с новым `[[proxy]]` отключает плагин.
- HTTP через прокси к тестовому серверу на `127.0.0.1:<порт>`: метод/путь/query/тело потоком,
  `Host` исходный, `X-Forwarded-*`, cookie сессии и `Authorization` не доходят, `Set-Cookie` сессии
  вырезан, `Location` переписан, CSP не подменён, без сессии — `401`, target лежит — `502`,
  выключенный плагин / пустая настройка — маршрута нет (отдаёт панель как раньше).
- WebSocket: эхо-сервер за прокси, сообщения в обе стороны, закрытие с любой стороны.
- `self-url`: совпадает с локальным адресом соединения к тестовому target; Host-guard с
  `only_listed_urls` пускает этот Host с адреса target на `/app/<id>/…` и не пускает на `/api/…`.
- Панель: `openFrame` на свой origin с путём прокси — да, на свой origin вне префиксов — ошибка.

## Что поменяет плагин rc-office после этого (делаю я, на стороне плагина)

- Манифест: `api = "^0.2.15"`, `[[proxy]]` как выше, убрать `frame = ["{office_url}"]`;
  `office_url` — «внутренний адрес Collabora (как его видит сервер облака)».
- Discovery — как сейчас, через `http.fetch` на `office_url`; в `urlsrc` origin Collabora заменяется
  на origin панели (`context.origin`) — редактор открывается через прокси.
- `WOPISrc` = `proxy.self-url()` + `/app/rc-office/wopi/files/<id>`; `wopi_base_url` остаётся
  необязательным переопределением (или уходит совсем).
- README и пример compose: Collabora без `ports` и без `aliasgroup1`.

## Отвергнутые варианты

- **Прокси в самом плагине** — нет WebSocket, CSP `sandbox`, лимиты 16 МБ / 60 с (см. «Зачем»).
- **Ядро само запускает CODE (как `richdocumentscode`)** — образ облака `read_only` + `cap_drop: ALL`,
  Collabora там работает только в слабом режиме без capabilities, ~770 МБ памяти внутри контейнера
  облака, нужен механизм нативных сервисов плагинов. Можно поверх прокси позже, если понадобится.
- **Префикс `/app/<id>/svc/…` + `net.service_root` у Collabora** — чище по путям (нет корневых
  префиксов), но снова настройка в compose, которая должна совпадать с плагином.

## Открытые вопросы для ядра

1. Корневые префиксы (`/browser`, `/cool`, `/hosting`) или `service_root`-вариант — выбор ядра;
   плагину годятся оба (во втором случае префикс задаёт ядро, а `self-url`/документация говорят
   администратору, какой `service_root` поставить).
2. HTTPS снаружи: проверить на стенде, строит ли Collabora `wss://` за прокси по `X-Forwarded-Proto`
   или ей нужен `--o:ssl.termination=true` (это статичный параметр, не адрес — допустимо в примере
   compose).
3. Имя вместо IP в `self-url` (PTR) — сразу или потом.
4. Анонимный доступ к прокси (`auth = "none"`) — не сейчас.
